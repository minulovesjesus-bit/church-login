# 교회 출결 UI 리디자인 설계

## 1. 목적

현재 서비스는 출결, 학생, 일정, 교사 승인, 키오스크 기능을 갖추고 있지만 화면별 스타일 완성도가 다르다. 특히 루트, 인증, 회원가입, 온보딩, 교사 신청 화면은 공통 레이아웃과 컴포넌트 스타일이 없어 브라우저 기본 UI처럼 보인다.

이번 작업은 기존 기능과 라우트를 유지하면서 모든 화면을 하나의 따뜻한 교회 커뮤니티 디자인 시스템으로 통합한다. 구현 기반은 기존 Next.js App Router, TypeScript, Tailwind CSS v4이며 UI 프리미티브는 shadcn/ui로 통일한다.

## 2. 승인된 시각 방향

- 분위기: 따뜻하고 안정적인 교회 커뮤니티
- 종교 표현: 작은 십자가와 열린 문 모티프만 은은하게 사용
- 배경: 순백색을 중심으로 사용하고 넓은 화면의 작업 영역에만 아주 옅은 세이지 배경을 허용
- 핵심 색상: 포레스트 그린, 소프트 세이지, 절제된 골드
- 형태: 12~20px의 둥근 모서리, 얇은 테두리, 최소한의 그림자
- 밀도: 학생 화면은 낮은 밀도와 큰 터치 영역, 교사 화면은 표 중심의 중간 밀도
- 이미지: 로그인 진입 화면의 열린 문과 자연광 장면만 핵심 이미지로 사용
- 금지: 과도한 십자가, 대형 교회 사진, 네온, 글래스모피즘, 의미 없는 배지, 벤토 그리드, 과도한 그라디언트

## 4. 기술 구조

### 4.1 프레임워크

- Next.js App Router와 기존 서버·클라이언트 컴포넌트 경계를 유지한다.
- Tailwind CSS v4와 `src/app/globals.css`의 semantic token을 사용한다.
- shadcn/ui는 프로젝트의 npm 실행기를 사용해 공식 CLI로 초기화한다.
- shadcn 컴포넌트는 `src/components/ui`에 소스 형태로 관리한다.
- 아이콘은 shadcn 설정이 선택한 동일 아이콘 라이브러리 하나만 사용한다.
- 기존 FastAPI, Supabase 인증, API 클라이언트 계약은 변경하지 않는다.

### 4.2 컴포넌트 계층

1. `src/components/ui`: shadcn 프리미티브와 프로젝트 공통 variant
2. `src/components/brand`: 브랜드 마크, 워드마크, 공통 로고
3. `src/components/layout`: 인증 셸, 학생 셸, 교사 셸, 키오스크 셸
4. `src/features/*`: 출결, 학생, 일정, 키오스크의 도메인 컴포넌트
5. `src/app/*`: 라우트 조합과 데이터 연결

페이지에서 색상과 타이포그래피를 직접 정의하지 않는다. 반복되는 상태, 버튼, 표, 폼, 알림은 공통 컴포넌트 또는 명시적 variant로 구현한다.

## 5. 디자인 토큰

### 5.1 색상

| 용도 | 값 | semantic token |
| --- | --- | --- |
| 기본 배경 | `#FFFFFF` | `--background` |
| 기본 텍스트 | `#202521` | `--foreground` |
| 주요 행동·사이드바 | `#173D2B` | `--primary` |
| 주요 행동 위 텍스트 | `#FFFFFF` | `--primary-foreground` |
| 연한 선택 배경 | `#E9F0EA` | `--secondary`, `--accent` |
| 보조 텍스트 | `#667169` | `--muted-foreground` |
| 테두리 | `#D8E1DA` | `--border`, `--input` |
| 골드 강조 | `#C9A75B` | `--brand-gold` |
| 성공 | `#2D7A50` | `--success` |
| 경고 | `#A8751B` | `--warning` |
| 오류 | `#B24A4A` | `--destructive` |

골드는 시간, 진행 상태, 작은 강조선에만 사용한다. 본문 텍스트나 넓은 배경색으로 사용하지 않는다.

### 5.2 타이포그래피

- 기본 서체: `Noto Sans KR`을 `next/font`로 자체 호스팅
- 본문: 15~16px, 400~500 weight, 1.55~1.7 line-height
- UI 제어 문자: 13~15px, 600~700 weight
- 모바일 페이지 제목: 28~34px, 700~800 weight
- 데스크톱 페이지 제목: 32~38px, 700~800 weight
- 숫자 지표: tabular numerals를 사용하고 숫자와 단위를 시각적으로 분리
- 영문 eyebrow는 제거하고 필요한 문맥은 한국어 제목과 설명으로 전달

### 5.3 공간과 형태

- 기본 간격 단위: 4px
- 페이지 gutter: 모바일 16px, 태블릿 24px, 데스크톱 32~40px
- 일반 control 높이: 44px 이상
- 모바일 핵심 CTA 높이: 64~72px
- 카드 radius: 16px, 핵심 패널 20px
- input/button radius: 10~12px
- 그림자: 떠 있는 레이어와 핵심 패널에만 낮은 강도로 사용
- focus ring: 포레스트 그린과 구분되는 밝은 세이지 외곽선, 3:1 이상의 인접 대비

## 6. shadcn/ui 사용 규칙

### 6.1 도입 대상

- 행동: `Button`
- 정보 컨테이너: `Card`
- 폼: `Field`, `FieldGroup`, `Input`, `Textarea`, `Select`
- 데이터: `Table`, `Badge`, `Avatar`
- 내비게이션: `Sidebar`, `Sheet`, `Tabs`, `Pagination`
- 피드백: `Alert`, `Skeleton`, `Spinner`, `Progress`, `Sonner`
- 오버레이: `Dialog`, `AlertDialog`, `DropdownMenu`
- 구조: `Separator`, `ScrollArea`

### 6.2 구성 원칙

- 색상은 raw Tailwind 색상이 아니라 semantic token을 사용한다.
- `className`은 레이아웃 조정에만 사용하고 shadcn 컴포넌트의 색상과 타이포그래피를 페이지에서 덮어쓰지 않는다.
- 폼은 `FieldGroup`과 `Field`를 사용하고 오류 시 `data-invalid`와 `aria-invalid`를 함께 설정한다.
- 알림, 로딩, 빈 상태, 배지는 각각 shadcn `Alert`, `Skeleton`, `Empty`, `Badge`로 통일한다.
- 모바일 교사 메뉴는 `Sheet`, 데스크톱 교사 메뉴는 `Sidebar`로 구성한다.
- 삭제나 비활성화 확인은 `AlertDialog`로 제공하고 제목을 반드시 포함한다.

## 7. 화면별 설계

### 7.1 루트와 인증

적용 라우트:

- `/`
- `/teacher/login`
- `/auth/login`
- `/auth/signup`
- `/onboarding`
- `/teacher/apply`

`AuthShell`을 공통으로 사용한다. 데스크톱은 좌측 정보·폼과 우측 열린 문 이미지의 2열 구조이며, 모바일에서는 이미지를 작은 상단 브랜드 장면으로 줄이고 폼을 먼저 노출한다.

루트 화면의 허용 문구:

- `교회 출결`
- `함께하는 오늘, 안심되는 출결`
- `학생과 교사가 한곳에서 출결과 일정을 확인해요.`
- `학생으로 로그인`
- `교사로 로그인`
- `학생 회원가입`

학생 로그인과 회원가입은 Google 행동과 이메일 폼을 `Separator`로 구분한다. 교사 로그인은 Google 행동 하나만 강조한다. 온보딩과 교사 신청은 같은 폼 셸을 공유하되 입력 내용은 기존 계약을 유지한다.

### 7.2 학생 화면

적용 라우트:

- `/student`
- `/student/scan`
- `/student/attendance`
- `/student/events`

모바일 우선으로 구현한다. 학생 홈은 오늘 상태, QR 핵심 행동, 이번 달 통계, 이번 주 일정 순서를 유지한다. 하단 내비게이션은 모바일에 고정하고 태블릿·데스크톱에서는 상단 내비게이션으로 전환한다.

- 오늘 상태는 한 개의 핵심 패널로 표현한다.
- `QR로 출결하기`는 화면에서 가장 강한 CTA다.
- 월간 통계는 세 개의 열린 열로 구성하고 불필요한 개별 카드를 만들지 않는다.
- 일정은 한 줄 이벤트 항목을 기본으로 사용한다.
- QR 스캔 화면은 카메라 영역을 최우선으로 하고 성공·오류·재시도 상태를 명확하게 구분한다.

### 7.3 교사와 관리자 화면

적용 라우트:

- `/teacher`
- `/teacher/attendance`
- `/teacher/students`
- `/teacher/events`
- `/teacher/applications`
- `/admin/staff`
- `/admin/kiosks`

데스크톱은 240~272px 고정 사이드바와 표 중심 작업 영역을 사용한다. 태블릿·모바일에서는 사이드바를 `Sheet`로 전환한다.

- 대시보드 요약은 큰 카드 그리드가 아니라 하나의 수평 지표 rail로 구성한다.
- 출결과 학생 관리는 desktop `Table`, mobile 행 카드/목록으로 전환한다.
- 필터와 검색은 표 바로 위에 배치한다.
- 일정은 주간 이동과 편집 폼을 같은 화면에서 명확하게 구분한다.
- 교사 승인, 권한 변경, 키오스크 세션 관리는 상태 `Badge`와 확인 `AlertDialog`를 사용한다.
- 실제 기능에 없는 검색, 알림, 그래프, 지표를 시각 장식으로 추가하지 않는다.

### 7.4 키오스크

적용 라우트:

- `/login`

잠금 상태는 관리자 비밀번호 입력에 집중하는 단일 폼으로 구성한다. 잠금 해제 상태는 대형 QR과 설명을 2열로 배치하고 화면 높이가 좁거나 portrait일 때 1열로 전환한다.

- QR은 최소 320px, 사용 가능한 공간에서는 420~520px로 표시한다.
- 20초 남은 시간을 숫자와 진행 표시로 동시에 제공한다.
- 연결 상태는 색상만이 아니라 텍스트로도 표시한다.
- `관리자 화면 잠금`은 시각적으로 조용하지만 항상 찾을 수 있어야 한다.
- QR 재발급 시 레이아웃이 흔들리지 않아야 한다.

## 8. 반응형 규칙

| 구간 | 주요 동작 |
| --- | --- |
| 0~639px | 학생 모바일 기준, 고정 하단 nav, 교사 nav는 Sheet, 표는 목록 전환 |
| 640~1023px | 태블릿 gutter 확대, 2열 가능한 영역만 분할, 키오스크 portrait 지원 |
| 1024px 이상 | 교사 고정 Sidebar, 학생 상단 nav, 인증 2열, 키오스크 landscape 2열 |

터치 대상은 모든 구간에서 최소 44×44px를 유지한다. 표가 목록으로 전환될 때 정보와 행동을 누락하지 않는다.

## 9. 상태와 오류 처리

- 인증·권한 확인: 전체 화면 `Skeleton` 또는 명확한 상태 메시지
- API 오류: `Alert`와 `다시 시도` 행동
- 성공: 폼 인접 메시지 또는 `Sonner` toast, 중요한 완료 상태는 페이지 내에서도 유지
- 빈 목록: `Empty`에 원인과 가능한 다음 행동 표시
- 저장 중: 버튼 비활성화와 `Spinner`, 중복 제출 방지
- 카메라 권한 오류: 원인, 브라우저 설정 안내, 다시 시도 행동
- 연결 불안정: 마지막 성공 데이터임을 명시하고 수동 재시도 제공

오류를 색상만으로 전달하지 않으며 `role`, `aria-live`, label 연결을 기존 테스트와 함께 유지한다.

## 10. 애니메이션

- 페이지 진입: 160~220ms의 짧은 opacity/translate 전환
- 버튼과 선택 상태: 120~160ms
- QR 타이머: 숫자 변경과 progress만 갱신하고 QR 컨테이너 크기는 고정
- 교사 모바일 Sheet: shadcn 기본 motion 사용
- `prefers-reduced-motion`에서는 비필수 전환을 제거

## 11. 구현 경계

이번 UI 리디자인에서 변경하지 않는 항목:

- FastAPI 엔드포인트와 응답 스키마
- Supabase 인증 흐름과 권한 규칙
- QR 토큰 지속 시간과 입실·퇴실 교대 규칙
- 학생 활성화·비활성화의 통계 의미
- 일정 반복 규칙
- 기존 라우트 URL

UI 구현 중 데이터 계약 변경이 필요해 보이면 임의로 수정하지 않고 별도 문제로 분리한다.

## 12. 테스트와 시각 검증

### 12.1 자동 검증

- 기존 Vitest와 Playwright 테스트를 유지한다.
- 변경된 접근성 이름과 역할을 테스트에 반영한다.
- `npm run lint`, `npm test`, `npm run build`를 실행한다.
- 핵심 경로 E2E: 루트 역할 선택, 학생 로그인/가입, 학생 QR 진입, 교사 로그인/승인, 교사 출결·학생·일정, 키오스크 잠금/해제.

### 12.2 시각 검증

- Browser/IAB에서 실제 렌더링을 우선 확인한다.
- 뷰포트: 390×844, 768×1024, 1024×768, 1440×900.
- 승인 시안과 실제 화면을 같은 크기로 캡처한다.
- `view_image`로 시안과 렌더를 함께 확인한다.
- 비교 항목: 카피, 구조, 타입 크기, 색상, 여백, 테두리/radius, 아이콘, 반응형 전환, 핵심 행동.
- 로그인 진입, 학생 홈, 교사 대시보드, 키오스크 네 화면은 시안 대비 수정 내역을 fidelity ledger로 기록한다.

## 13. 완료 기준

- 모든 라우트가 공통 디자인 시스템을 사용한다.
- 브라우저 기본 스타일로 보이는 버튼, 폼, 링크가 남아 있지 않다.
